# Deploying to Render

The repository ships a Render Blueprint (`render.yaml`), so the whole stack —
web service, Postgres, and a disk for uploads — comes up from one screen.

## Before you start

Nothing. No API keys, no external accounts. Media is stored on a Render disk to
begin with; you can move it to object storage later without a code change.

## 1. Create the blueprint

1. Push the branch you want to deploy (this guide assumes
   `claude/epic-hypatia-n6s81y`; change `branch:` in `render.yaml` for `main`).
2. Render dashboard → **New** → **Blueprint**.
3. Pick the `comlabs-technologies/mavryn` repository and approve the plan.

Render reads `render.yaml` and creates:

| Resource | Notes |
|---|---|
| `comlabs-cms-db` | Managed Postgres. `DATABASE_URL` is wired to the web service automatically. |
| `comlabs-cms` | The web service, built from `docker/Dockerfile`. |
| `comlabs-cms-media` | A 1 GB disk mounted at `/app/.media`. |

`BETTER_AUTH_SECRET` is generated by Render. You do not set it, and you should
not regenerate it later — doing so signs every user out.

## 2. Wait for the first build

The Docker build runs `pnpm install --frozen-lockfile`, generates the Prisma
client, then builds Next in standalone mode. Expect several minutes on the
first deploy; later builds reuse cached layers.

On boot, `docker/entrypoint.sh` runs `prisma migrate deploy` before starting
the server. That is safe on every restart — it only applies migrations that
have not run yet, and never resets anything.

## 3. Check it came up

Render polls `/api/health`, which runs `SELECT 1`. A healthy response looks
like:

```json
{ "status": "ok", "database": "reachable", "latencyMs": 3 }
```

If the service is live but unhealthy, the database is the thing to look at
first — usually a region mismatch between the service and the database.

## 4. Create your account

Open the service URL and sign up. The first screen after sign-up creates your
organization; Blog and Case Study content types are created with it.

To fill it with demo content, use Render's **Shell** tab on the web service:

```sh
cd /app/migrator && node ./node_modules/.bin/prisma studio   # or, for content:
```

Or run the demo seed from your own machine against the external connection
string (copy it from the database's dashboard page):

```bash
DATABASE_URL="<external connection string>" \
LOCAL_MEDIA_DIR=/tmp/media \
pnpm db:demo
```

Cover images written this way land on your machine rather than the server's
disk, so upload images through the dashboard instead if you want them served.

## 5. Custom domain

Add the domain on the web service, then set `BETTER_AUTH_URL` to
`https://your-domain.com`. Until you do, the app derives its URL from
`RENDER_EXTERNAL_URL` at runtime, so it works on the `onrender.com` subdomain
without any configuration.

## Moving media to object storage

The disk is the simplest thing that works, but it pins the service to one
instance and prevents zero-downtime deploys. When that starts to matter, create
a Cloudflare R2 bucket and change these environment variables:

```
MEDIA_PROVIDER      = s3
S3_BUCKET           = your-bucket
S3_ENDPOINT         = https://<account-id>.r2.cloudflarestorage.com
S3_REGION           = auto
S3_ACCESS_KEY_ID    = ...
S3_SECRET_ACCESS_KEY= ...
S3_PUBLIC_BASE_URL  = https://cdn.your-domain.com
```

Then remove the disk from `render.yaml`. Images already on the disk keep their
`/uploads/...` URLs and stop resolving, so re-upload them or copy the disk
contents into the bucket first.

## Things that will bite you

- **Free Postgres expires.** Render's free databases are time-limited. Move to
  a paid plan before you have content you would miss, and check that backups
  are on.
- **Region mismatch.** The service and database must be in the same region, or
  every query pays cross-region latency.
- **Free web instances sleep.** A sleeping instance takes a while to answer the
  first request, which looks like an outage to a site reading your API.
- **The read API is uncached.** Every `GET /api/v1/content` is a database round
  trip today. Put a CDN in front, or add `s-maxage` to those routes, before
  pointing a production site at it.
